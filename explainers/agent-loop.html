What happens when an agent reads your prompt.

Six sections, one idea: an agent is a program passing text to a text predictor, over and over. Everything that feels mysterious about it — memory, tools, context limits, cost — falls out of that one arrangement.

01 / the mental model · keep this one

What an agent actually is

An agent is a conversation between a harness — the orchestrator program — and a model, which is a text predictor. The harness hands over a big blob of text; the model hands back text. That exchange is the whole game.

Everything else here is detail on those two arrows: what is in the context the harness sends, and what the harness does with the text it gets back.

02 / the first arrow · what the model is handed

Context is everything the model sees

The model has no window into your machine. Before every call the harness assembles one request — a single stack of text. If something is not in this stack, the model does not know it exists.

03 / the signature move · the loop

One prompt becomes many turns

The reply usually is not an answer yet — it is a request to do something. So the harness acts, folds the result back into the context, and asks again. Around and around, until the model has nothing left to ask for.

Steps 1 and 4 are bookkeeping

The harness builds the text going in, and stitches results back in after.

Step 2 is the only model call

It thinks once, then yields control. It cannot act on its own.

Step 3 is the real work

Files get read, tests get run, edits get applied — all by the harness.

04 / the detail that makes it click

Memory is the harness re-feeding the whole transcript

Because the model forgets everything between calls, the harness cannot just send the new result. It re-sends the entire growing history every single turn. Each call is bigger than the last.

This is why agents have a context limit, and why long sessions slow down or start forgetting early details. The transcript eventually gets too big to re-send in full, so the harness has to trim it or summarize it.

05 / look closer · one request, fully expanded

What each turn actually sends

The seven sources are not seven floating slots. The harness lays them out as one ordered sequence: the stable three at the top, then the conversation — and the conversation absorbs file snippets and tool results as it grows.

Turn 4's reply is what closes the cycle

11 · Assistant (final): “Added logging middleware — 12 tests pass.” // no tool call → the harness stops looping // and hands this back to you

Row 11 is the model's reply to turn 4. It is not sent in another request; it is the output that ends the loop. Whatever you type next appends as row 12, and the harness fires turn 5 on top of all eleven rows — the same cycle, continued.

So the conversation so far is everything from row 4 down — and it is not only your messages.

The model's own replies, the files it read, and every tool result are all entries in that one growing list. File snippets and previous tool results are not separate slots beside the conversation — they enter the conversation as tool-result messages, in order, and then never change.

One simplification: this example does a single tool call per turn — read, then edit, then test — to keep the steps legible. A real agent often batches several calls into one reply, which collapses this into fewer turns. The append-only growth is identical either way; only the number of turns changes.

06 / the payoff · why append-only matters

Why the prefix has to stay byte-for-byte identical

A model normally re-reads its entire input from scratch on every call. The KV cache is how it avoids that: for every token it has already processed it stores the intermediate attention values — the keys and values. Hand it the exact same opening sequence again and it skips straight past those tokens, computing only what is new at the end.

That is the real reason the harness re-sends everything unchanged and only appends. Each turn, the long stable prefix and the entire prior conversation are a cache hit. Because the model already computed its own replies while generating them, the only genuinely new text it has to read each turn is the tool results the harness just handed back.

Change anything early and every cached value after the change is invalid.

Edit AGENTS.md or the system prompt, reorder messages, or trim and summarize old turns to fit the context limit — the model has to recompute from that point on. Append-only is cheap; rewriting history is expensive. It is why editing AGENTS.md mid-session costs more than it looks: it sits near the top, so the whole conversation below it falls out of cache. And it is why trimming a long conversation — the fix section 04 ends on — is not free either.
