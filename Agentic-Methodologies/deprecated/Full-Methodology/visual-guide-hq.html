A developer’s first mental model

Don’t ask the agent to remember the project.

Make the repository remember.

The methodology turns product intent, engineering decisions, active work, and proof into durable repository artifacts. Chat helps the work happen. Git preserves what the work means.

The reusable mental model

Two truths. One bridge. One lock.

This model explains where information belongs, why planning may be ahead, how implementation becomes trustworthy, and why only one task executes at a time.

Truth 1 specs/

Intended behavior

Product and business behavior the system should have. Specs may describe work not implemented yet.

Ahead is allowed. Contradiction is not.

Truth 2 tests ↔ code ↔ docs

Implemented behavior

What the system actually does, how it is proved, and how it is explained. These must stay in Omni-Sync.

Built behavior must agree everywhere.

Route before you act

A request is work. Its route determines the rigor.

The root router sends each request to the smallest governing procedure that fits. Every repository-changing route first checks agent/tasks/CURRENT.md.

1. Check CURRENT.md

If another task is active, serve it or ask the engineer to resolve the conflict.

Context without overload

Read a route, not the whole repository.

Control files have different jobs. Their separation keeps rules stable, procedures bounded, and durable project facts in the right home.

AGENTS.md

Project contract

Stack, stable paths, commands, standards, safety, approvals, and prohibited actions.

CONTEXT.md

Area governor

Routing, canonical paths, invariants, boundaries, and rules that always apply in an area.

SKILL.md

Bounded procedure

Explicit trigger, ordered steps, guardrails, references, and a defined output.

templates/

Artifact shape

The expected structure of a brief, plan, progress record, or other repeatable artifact.

A large lifecycle is not automatically a skill.

The full six-step task workflow remains in agent/tasks/CONTEXT.md. Skills support bounded procedures such as updating specs, creating tasks, auditing drift, or reviewing code.

Execution is a control loop

Six checkpoints. Five review moments. Evidence throughout.

The sequence is ordered, but it is not a blind waterfall. Verification findings, implementation surprises, or material design changes send the task back to the appropriate earlier step.

  1. 1

    Assess and approve the plan

    Explicit approval

    Reconcile specs, brief, plan, code, tests, docs, and architecture boundaries. No application code yet.

  2. 2

    Create tests or checks

    Engineer review

    Express acceptance criteria as behavior-focused proof before implementation when feasible.

  3. 3

    Implement the approved plan

    Engineer review

    Keep scope tight. Dependencies, migrations, services, and public API changes need approval.

  4. 4

    Verify and repair

    Review after pass

    Run narrow checks, broaden by risk, record failures honestly, and use the code-review skill when required.

  5. 5

    Update implementation docs

    Engineer review

    Describe actual behavior and review whether architecture boundaries changed.

  6. 6

    Conclude and handle the commit

    Commit approval

    Finalize evidence, update activity, move the task to done/, and release the lock.

Before each handoff

  • Update PROGRESS.md.
  • Record the current step and next action.
  • Run applicable lint or non-mutating format checks for steps 2, 3, and 5.
  • Do not call a failing required check a pass.

When work loops backward

  • New design or material scope: return to step 1.
  • Missing behavioral proof: return to step 2.
  • Review defect: return to the step that owns the repair.
  • Unrelated failure: record it separately; do not conceal it.

Gate override

The engineer may explicitly waive a review gate for a task. The waiver and its scope remain durable in PROGRESS.md.

What “done” means

A task closes with a chain of evidence, not a confident summary.

Traceability connects the task’s local requirement to the observable result and every artifact that proves, implements, and explains it.

Concrete walkthrough

Follow one feature across three sessions.

This illustrative request shows how repository artifacts preserve continuity even when the conversation, tool, or agent session changes.

Session 1 planning
“Create a feature task for saved searches. Do not execute it.”

1. Read CURRENT.md.

2. Verify specs authorize the behavior.

3. Use create-task.

4. Create the brief, draft plan, progress record, and activity entry.

Result: a formal task exists, but no implementation has started.

Session 2 step 1
“Assess and begin the saved-searches task. Stop after plan review.”

1. Set CURRENT.md to the task path.

2. Reconcile the task with current code and architecture.

3. Update PLAN.md and PROGRESS.md.

4. Ask for explicit plan approval.

Result: the lock remains occupied while waiting for review.

Session 3 resume
“Resume the task in CURRENT.md from its recorded next action.”

1. Read root controls, lock, brief, plan, and progress.

2. Continue from Next action, not chat memory.

3. Advance through tests, implementation, verification, docs, and closure.

4. Release the lock only after completion handling is recorded.

Result: continuity survives the session boundary.

Why the example matters

The method does not rely on one enormous uninterrupted conversation. The task package captures intent, approved design, evidence, decisions, and the exact next action well enough for work to resume safely.

Category mistakes to avoid

Five distinctions keep the system honest.

01

Prompt ≠ task

A task has durable artifacts, progress, evidence, and a lifecycle.

02

Candidate ≠ task

A broad-plan slice is guidance until formal task artifacts are created.

03

Spec gap ≠ drift

Intended behavior may be unimplemented without violating Omni-Sync.

04

Plan ≠ app docs

Plans describe intended implementation; docs describe the system actually built.

05

Code changed ≠ done

Done includes proof, documentation impact, traceability, risk, and closure handling.

The skill shelf

Use a bounded procedure when it has a clear trigger.

A skill is selected because the work matches its purpose, not merely because the skill exists.

update-specs

Change product intent, check task conflicts, and snapshot the accepted spec set.

plan-feature-work

Map broad accepted intent into ordered candidate slices without creating tasks.

create-task

Create the correct formal task package without starting execution.

planning-audit

Check deprecated tasks, missed specs, implementation, or conflicting active state.

drift-audit

Diagnose disagreement among implemented behavior, proof, code, and docs.

docs-refinement

Improve implemented-system documentation without changing runtime behavior.

clarify-with-shared-language

Resolve one design branch at a time using shared terminology and repository evidence.

improve-codebase-architecture

Find evidence-backed opportunities for deeper modules and stronger locality.

code-review

Run a structured second pass over a task diff when risk, deviation, complexity, or the engineer requires it.

Your first week

Learn the method through one small real task.

Do not begin by customizing every artifact. Use the scaffold, observe where it helps or adds friction, and improve it from repeated evidence.

  1. 1

    Read the controls

    AGENTS.md, root CONTEXT.md, then CURRENT.md.

  2. 2

    Choose a narrow, real change

    Prefer something useful enough to matter and small enough to review clearly.

  3. 3

    Create or select the formal task

    Keep intent in the brief, design in the plan, and execution truth in progress.

  4. 4

    Review evidence, not just prose

    Inspect the actual diff, tests, commands, docs, traceability, and residual risk.

The sentence to remember

Specs hold intended truth. Tests, code, and docs hold current truth. A task bridges one change. CURRENT.md permits one bridge at a time.
