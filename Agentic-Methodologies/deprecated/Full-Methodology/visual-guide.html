Beginner guide

The core lesson

The repository is the shared memory.

You remain the strategist. The agent investigates and executes one governed line of work at a time. Specs, task files, tests, code, and documentation preserve the truth after the chat ends.

Engineer decides One active task Evidence stays in Git

Why this exists

Chat is useful workspace. It is poor project memory.

Before

Work lives in conversation

  • ×Scope and decisions disappear across sessions.
  • ×“Done” can mean code changed, even when tests or docs disagree.
  • ×Several prompts can quietly become several competing workstreams.
  • ×The engineer reviews summaries instead of durable evidence.
With the methodology

Work leaves a trail

  • ✓Specs hold intended product behavior.
  • ✓Task files hold scope, plan, progress, and evidence.
  • ✓CURRENT.md names the one active task.
  • ✓The engineer reviews checkpoints, the actual diff, and verification.

Reusable mental model

Four layers. One source of truth for each fact.

Ask which layer owns the information before adding it. Routing files tell the agent what to read next, without loading the entire repository.

Retell it this way: specs say what should exist; tasks govern a change; code, tests, and docs say what exists now; control files route and constrain the work.

Words with precise meanings

Learn these four terms first.

Task

formal

A repository-tracked development work item with scope, artifacts, progress, evidence, and a lifecycle.

A prompt is not automatically a task.

Work

general

Anything requested from or performed by the agent: planning, task execution, an audit, or an approved informal change.

All tasks are work. Not all work is a task.

TPT

progress

Task Progress Tracking is the resumable execution record inside the active task’s PROGRESS.md.

It says where execution is and what evidence exists.

Omni-Sync

consistency

Tests and contracts, code, and implementation documentation agree about behavior already built.

An unimplemented spec is not automatically drift.

Not every request enters the six-step workflow.

First read agent/tasks/CURRENT.md. If it names a task, unrelated work waits. If it says none, choose the route that matches the request.

Start at the root. Follow the route.

You do not need to memorize every file. Read the root instructions, check the lock, then enter only the area relevant to the work.

Formal task execution

Six checkpoints turn a request into reviewed evidence.

The agent updates PROGRESS.md before every handoff. The engineer may waive a gate explicitly, but the waiver is recorded.

1

Approve

Assess the plan

Reconcile specs, brief, plan, code, tests, docs, and architecture boundaries.

2

Review

Create tests

Express acceptance criteria as tests or credible executable checks before implementation where feasible.

3

Review

Implement

Make the approved scoped change. Return to step 1 if design or scope changes materially.

4

Verify

Check and repair

Run narrow checks, broaden by risk, repair failures, and run structured code review when required.

5

Review

Update docs

Document actual behavior and review whether architecture boundaries changed.

6

Approve commit

Conclude

Finalize traceability, residual risk, activity status, task move, and lock release.

Before execution: CURRENT.md changes from none to the task path.
→
After approved closure: the task moves under done/ and the lock returns to none.

Skills are tools, not the operating system

Use a skill when its bounded procedure matches the work.

CONTEXT.md owns governing rules and routing. A SKILL.md owns explicit triggers, ordered steps, guardrails, and output. Formal task execution remains in agent/tasks/CONTEXT.md.

Who decides what?

The agent has autonomy inside explicit boundaries.

The system is intentionally not “agent runs until done.” It is a collaboration where routine investigation and verification move quickly, while product direction and consequential changes stay with the engineer.

Agent

Investigates and executes

  • Reads routed repository context
  • Challenges contradictions and unsafe plans
  • Edits within approved scope
  • Runs proportionate verification
  • Records progress, evidence, and residual risk

Engineer

Sets direction and approves

  • Chooses product direction and tradeoffs
  • Resolves spec and task conflicts
  • Approves the implementation plan
  • Reviews checkpoints and the actual diff
  • Approves dependencies, migrations, APIs, and commits

Your first session

Start with the route, not with a giant prompt.

The methodology becomes understandable through one small real task. Let the repository tell both you and the agent where the work belongs.

  1. 1

    Read the project controls

    AGENTS.md, then root CONTEXT.md.

  2. 2

    Check the active-task lock

    Read agent/tasks/CURRENT.md before repository-changing work.

  3. 3

    Choose the correct work route

    Planning, formal task execution, complementary skill, or an explicitly confirmed informal exception.

  4. 4

    Use one small real task to learn

    Review its brief, plan, progress, tests, diff, documentation, and closure evidence.

Remember this

Intent in specs. Work in tasks. Reality in code, tests, and docs. Decisions with the engineer.
